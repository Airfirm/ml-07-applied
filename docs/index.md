## Phase 4. Technical Modification

For my technical modification, I updated the project with a new notebook named:

- `notebooks/ml_07_femi.ipynb`

This notebook keeps the original idea of investigating a deployed Penguin prediction model, but adds a stronger testing workflow and structured logging.

### What I Changed

I modified the notebook to:

- call a live prediction API with `requests`
- add retry and timeout handling for sleeping deployed servers
- create structured DataFrames from API responses
- run a `bill_length_mm` feature sweep to find a decision shift
- test edge cases and API error handling
- save visuals to `docs/images/`
- write notebook progress and summary results to the root `project.log`

The logging section uses `LOG.info(...)` so the notebook produces evidence in `project.log`, similar to the course example logs.

### Why I Chose This Change

I chose this change because the project log showed that the deployed API sometimes timed out when the server may have been sleeping. That is a realistic issue when working with deployed services.
Adding retry and timeout handling makes the notebook more reliable and helps document when the API returns predictions, errors, or timeout messages.

### How I Verified It Worked

I verified the modification by running the notebook and checking that it:

- confirmed the installation and package versions
- called the API endpoint
- created baseline prediction results
- ran the `bill_length_mm` sweep
- tested edge cases
- saved charts in `docs/images/`
- appended summary information to `project.log`

### Results and Visuals

The feature sweep showed that smaller `bill_length_mm` values predicted **Adelie**, while larger values predicted **Chinstrap**. The decision shift appeared around `bill_length_mm = 42.631579`.

![Bill Length Feature Sweep](./images/ml_07_femi_bill_length_sweep.png)

The edge case results showed that a missing feature returned an API error, while unusual numeric values still returned predictions.
This helped show which inputs were handled cleanly and which inputs exposed weaknesses in the API contract.

![Edge Case API Outcomes](./images/ml_07_femi_edge_case_outcomes.png)

### Challenge Level

This modification was moderately challenging because the notebook had to handle a live deployed service.
A local script usually runs the same way each time, but a deployed server can sleep, time out, or return errors.
Adding logging also required making sure the notebook wrote to the root `project.log` even when the notebook was running from the `notebooks/` folder.

## Phase 5. Custom Project

For my custom project, I added a second notebook named:

- `notebooks/ml_07_text_and_image_femi.ipynb`

This notebook applies the Module 7 skills to text and image analysis results. Instead of calling the Penguin predictor only, it studies API-style JSON results from image and text examples.

### Basis and API-Style Results

The custom notebook uses API-style JSON responses stored as Python dictionaries. The examples include:

- a good image label match with puppies
- an incomplete image result using a duck-rabbit optical illusion
- an interesting image result using a human-like robot
- sample text sentiment results

This approach connects to cognitive services because many cloud AI services return nested JSON containing labels, confidence values, categories, and detected attributes.

### Investigation Approach

I investigated the results by:

- storing JSON-style responses in Python dictionaries
- flattening nested image label JSON into pandas DataFrames
- comparing good, incomplete, and interesting image results
- summarizing confidence values
- creating charts from image label confidence and text sentiment confidence
- saving charts to `docs/images/`
- writing the results to `project.log` with `LOG.info(...)`

### Findings: Image Labels

The image results showed that clear realistic photos worked best. The puppy image produced strong labels such as animal, dog, puppy, pet, and grass.
The optical illusion was more difficult because the service could label it as art, drawing, animal, or bird, but it could miss the second interpretation as a rabbit.
The robot example was interesting because the service could identify the subject as a robot but also apply person-related labels when the object looked human-like.

![Top Image Label Confidence Values](./images/ml_07_text_image_label_confidence.png)

### Findings: Text Sentiment

The text examples showed how confidence values can be organized into a structured table. This makes it easier to compare results and explain which examples the service seemed most confident about.

![Text Sentiment Confidence Values](./images/ml_07_text_sentiment_confidence.png)

### Findings: Edge Cases and Incomplete Results

The custom investigation showed that AI services can return high-confidence results while still missing important human interpretation.
For example, an optical illusion may be recognized as a drawing or bird, but the service may miss that it can also be viewed as a rabbit.
This shows why confidence values should not be treated as perfect understanding.

### Summary

This project helped me learn that deployed AI models and cognitive services should be tested carefully.
The Penguin API investigation showed how predictions can shift when one feature changes and how edge cases can reveal API limitations.
The text and image notebook showed how nested JSON responses can be converted into structured DataFrames and visuals.

The model and service appear strongest when inputs are clear, common, and similar to expected examples. They appear more fragile when inputs are missing, unusual, ambiguous, or require human interpretation.
I would improve the API contract by adding stronger validation for unrealistic numeric values and clearer error messages for invalid input.

These techniques could apply to many real problems, including product classification, customer prediction, image tagging, sentiment analysis, and testing deployed business prediction APIs.
